# フォーカス管理の再設計

`docs/planning/next_version_backlog.md` の項目12（フォーカス管理の時間依存の整理）と、項目5・項目4の土台になる設計。**フォーカスの問題は不具合として実害が出ており、キー処理の整理（項目5）と UI 刷新（項目4）の前提になる**ため、先行して設計する。

## 要件

2026-10-27 にユーザーと合意した内容。

1. **`delay` を多用せず、素早く動くこと。** 現状は固定時間待ってからフォーカスを要求しており、高速機では無駄な待ち時間、低スペック機では待ち足らずという両方の問題を抱えている。
2. **これまでに得た「フォーカスを逃さない」知見を活かすこと。** 実機検証で判明した事実（後述）を設計に織り込む。
3. **フォーカス迷子検知の仕組みは根本から見直す。** 現状の自動復帰は、オーバーレイとの競合という別の不具合を生んでいる。
4. **復帰位置は画面ごとに決める。** 一律のルールを押し付けない。
5. **段階移行でよい。** 画面単位で移行し、そのたびに実機確認する前提。壊してはならない画面の指定はなし。

### 優先順位

実機で遅さ・不安定さを感じている画面から着手する。

| 順 | 画面 | `delay` | フォーカス要求 |
|---|---|---|---|
| 1 | `HomeLauncherScreen`（ホーム・タブ切替） | 12 | 22 |
| 2 | `RecordListScreen` / `RecordListContent`（録画一覧・詳細パネル） | 11 | 25 |
| 3 | `LivePlayerScreen`（ライブ視聴中） | 10 | 11 |

番組表（`EpgNavigationContainer` / `ModernEpgCanvasEngine`）は今回の対象外。Canvas 描画でグリッド全体が1つのフォーカス対象という特殊な構造であり、体感上の問題も報告されていない。

## 現状の問題

### 問題1: 待ち方が固定時間になっている

`safeRequestFocusWithRetry` は**成功すれば即座に返る**良い設計だが、実際の呼び出しは「先に固定時間待ってから、リトライなし版を1回だけ呼ぶ」形が大半。

```kotlin
LaunchedEffect(...) {
    delay(100)                            // 固定で待つ
    focusRequester.safeRequestFocus(TAG)  // リトライなしで1回だけ
}
```

これが「高速機では無駄、低スペック機では足りない」の直接の原因。`HomeLauncherScreen.kt:54` に「以前は各タブで一律 `delay(500)`〜`delay(800)` を挟んでいた」というコメントが残っており、**この方向の調整が繰り返されてきた**ことが分かる。値を詰めるだけでは解決しない。

### 問題2: フォーカスを奪われる経路が3つある

実機検証で判明した3パターン。**それぞれ対策が異なり、1つを塞いでも他が残る。**

| # | 経路 | 対策 | 効かないもの |
|---|---|---|---|
| 1 | 方向キーでオーバーレイの外へ出る | `focusProperties` で `FocusRequester.Cancel`、または `onKeyEvent` でキーを消費 | — |
| 2 | 戻るキーがフォーカス位置に届かない | `BackHandler`（`OnBackPressedDispatcher` 経由） | Compose のキーイベントはフォーカス要素とその祖先にしか届かない |
| 3 | **プログラムからの `requestFocus()` による奪取** | オーバーレイ表示中であることを復帰機構側へ伝える | **`focusProperties` では防げない** |

### 問題3: `focusProperties` は付ける場所の条件が厳しい

| 付けた場所 | 効くか |
|---|---|
| 親のレイアウト（`Column` 等、フォーカスを持たないノード） | **効かない** |
| `Surface(onClick = …)`（TV Material3、内部に `focusable` を持つ）に外から | **効かない**（内部 `focusable` の祖先になり、Compose 1.7 以降は継承されない） |
| `Modifier.focusProperties{}` と `Modifier.focusable()` を**同一チェーンに並べる** | 効く |
| `onKeyEvent` でキーを消費 | 効く |

加えて `focusProperties` を安易に足すと**入る方向の移動まで壊れる**（本文側に `right`/`up`/`down` の Cancel を足したら一覧から本文へ入れなくなった実例）。

### 問題4: 対策手法が5通りに分散している

| 画面 | 採っている手法 |
|---|---|
| `DeviceCapabilitiesScreen` | 各要素の `focusProperties` |
| `OpenSourceLicensesScreen` | `onKeyEvent` でキー消費 ＋ `BackHandler` |
| `SyncErrorDialog` | `focusProperties` ＋ `BackHandler` ＋ 抑制条件への登録 |
| `RobustUpdateDialog` | `focusGroup()` ＋ `exit = Cancel` ＋ **自前のフォーカス奪還** |
| `SettingScreen` | `focusProperties { canFocus = !isDialogOpen }`（Compose 1.7 以降は機能していない） |

`RobustUpdateDialog` の「奪われたら奪い返す」方式は、ホーム側の迷子検知と**互いに奪い合う**可能性がある。

### 問題5: オーバーレイを2箇所へ手で登録する必要がある

全画面オーバーレイを追加するたび、以下の**両方**へ登録しないと「表示されているのにフォーカスを奪われて操作できない」不具合になる。

| 箇所 | 役割 |
|---|---|
| `MainRootBackground.isBackgroundFocusBlocked` | 背面ツリーをフォーカス不可にする |
| `HomeLauncherScreen.isFocusSuspended` | フォーカス迷子検知を止める |

設定画面と AI コンシェルジュは登録済みだったが、同期エラーダイアログは**両方から漏れていた**（PR #123 で修正）。**構造的に再発する。**

## 設計方針

### A. 待ち方をフレーム単位にする

固定時間の `delay` をやめ、**即座に試して、失敗したら次フレームまで待つ**形にする。

```kotlin
/**
 * フォーカス対象が配置されるまで待ってから要求する。
 * 成功すれば待ち時間ゼロ。失敗時はフレーム単位(約16ms)で再試行する。
 */
suspend fun FocusRequester.requestFocusWhenReady(
    tag: String = "KomorebiFocus",
    maxFrames: Int = 10,               // 約160ms 相当
    shouldContinue: () -> Boolean = { true }
): Boolean
```

- 成功すれば**待ち時間ゼロ**（現状は最低 100ms 待つ）
- 失敗しても **16ms 単位**で再試行（現状の 100ms / 220ms より細かい）
- 10フレームで約160ms。現状の `delay(120)` + `delay(220)×4`（最大約1秒）より速く、試行回数は多い

`withFrameNanos` を使う。composition・layout が終わった次のフレームでは `FocusRequester` が attach されているため、通常は1〜2フレームで成功する。

### B. 確実性が要る箇所は `onPlaced` を使う

リストの初期フォーカスなど「配置されたら必ず当てたい」箇所は、レイアウト完了を検知してから要求する。リトライ自体が不要になる。

```kotlin
Modifier.onPlaced { /* ここで requestFocus すれば確実 */ }
```

A と B の二段構えにし、**B が使える箇所は B を優先**する。A は「状態変化に応じて後からフォーカスを移す」用途に残す。

### C. 迷子検知を見直す

現状はポーリングではなく状態駆動（`LaunchedEffect` のキーに `launcherHasFocus` / `contentFocusStranded`）だが、検知後に `delay(120)` → `delay(220)` と待つため復帰が遅い。また、オーバーレイとの競合を `isFocusSuspended` で抑えている。

**廃止はしない。** 操作不能になるリスクが大きすぎる。代わりに次の3点を変える。

1. **検知したら即座に試す**（A のヘルパーを使う）。待ってから試す形をやめる
2. **抑制条件を一元化**（D）。オーバーレイごとに手で足す形をやめる
3. **フォーカスを失う状況自体を減らす**（A・B により、そもそも復帰が必要な場面を減らす）

3 が本質。迷子検知は「設計の穴を埋める保険」であり、保険が頻繁に発動する状態そのものが問題。

### D. オーバーレイの登録を1箇所にまとめる

`MainRootState` に**表示中の全画面オーバーレイを表す単一の値**を持たせ、`isBackgroundFocusBlocked` と `isFocusSuspended` の両方がそれを参照する。

PR #123 で `isSyncErrorVisible` を `MainRootState` へ持たせ、表示条件を `MainRootScreen` で一元化した形を踏襲・一般化する。オーバーレイを追加したら1箇所の登録で済むようにし、**登録漏れが起きない構造**にする。

### E. 復帰位置は画面ごとに定義する

一律のルールにしない（要件4）。画面ごとに「どこへ戻すか」を明示的に持たせる。

- **一覧系**（録画一覧・ホームのカード列）: 直前の位置を復元する。`restoreFocusRequester` の考え方を維持・強化
- **ダイアログ・オーバーレイを閉じたあと**: 呼び出し元のボタンへ戻す
- **プレイヤーから戻ったあと**: 開く前に見ていた項目へ戻す（`isReturningFromPlayer` の仕組みを整理して残す）

### F. 手法を統一する

問題4の5通りを、以下に揃える。

| 目的 | 採用する手法 |
|---|---|
| 方向キーで外へ出さない | **フォーカスを持つ要素自身**の `focusProperties`。内部に `focusable` を持つコンポーネント（TV Material3 の Surface 等）には `onKeyEvent` でキー消費 |
| 戻るキーを確実に受ける | `BackHandler`。各要素への `onKeyEvent` 散布はやめる |
| プログラムからの奪取を防ぐ | D の一元化した登録を参照 |
| 奪われたら奪い返す | **採用しない**（`RobustUpdateDialog` の方式は迷子検知と競合する） |

共通ラッパー（`OverlayScreen(onBack = …) { … }` のような Composable）にまとめられるか、設計の実装段階で検証する。**新旧が共存できるインターフェースにすること**が要件（214箇所を一括変更はできない）。

## 移行計画

画面単位で進め、各段階で実機確認する。

| 段階 | 内容 | 確認すること |
|---|---|---|
| 0 | 共通ヘルパー（A・B）を追加。既存呼び出しは変えない | 既存挙動が変わらないこと |
| 1 | `RecordListScreen` / `RecordListContent` を移行 | 一覧のスクロール位置と詳細パネルの開閉、復帰位置 |
| 2 | `HomeLauncherScreen` を移行。あわせて C・D を実施 | タブ切替、プレイヤーからの復帰、オーバーレイ表示中の抑制 |
| 3 | `LivePlayerScreen` を移行 | サブメニュー・チャンネルリスト・2画面の開閉 |
| 4 | 残りの画面・ダイアログを F の方針で揃える | オーバーレイごとの戻るキーと閉じ込め |

段階1を録画一覧からにするのは、**影響範囲が閉じていて検証しやすい**ため（ホームは迷子検知とオーバーレイ抑制が絡む）。

## 検証方法

- **体感確認**: 画面遷移時にフォーカス枠が出るまでの待ち、リモコン連打への追従
- **低スペック機での確認は不可**（手元に該当機なし）。Fire TV Stick 4K Max 第1世代と REGZA 55X8900K で確認する
- **数値計測**: 項目10 で整備済みの `baselineprofile` の frameTimings を流用できる。フォーカス移動時のジャンクを測る

## 未決事項

実装段階で判断する。

- 共通ラッパー（`OverlayScreen`）にまとめるか、ヘルパー関数の組み合わせに留めるか
- `maxFrames` の既定値（10フレーム ≒ 160ms が妥当か、実機で詰める）
- `OpenSourceLicensesScreen` の残件（本文→一覧へ戻れない。`listFocusRequester` が先頭項目にのみ付いており、`LazyColumn` の項目が画面外に出ると対象を失う）は項目4の作り替えで対応する予定だが、E の「最後にフォーカスされていた項目へ戻す」仕組みを先に作れば解消する可能性がある
